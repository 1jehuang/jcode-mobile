## Highest-priority concrete wiring defects

### P1: Failed launcher shortcut publication is cached as successful

- **Call chain:** `MobileApp::system_tick` in `src/app/ios_system.rs` -> `system::index_sessions` in `src/system.rs` -> Android `imp::index` -> JNI `indexSessions` -> `AndroidServices.indexSessions` in `android/app/src/main/java/org/jcode/mobile/AndroidServices.java`.
- `IndexCache::prepare` advances the stored fingerprint before `imp::index` executes. The Android method can return false while `ShortcutManager.isRateLimitingActive()` or `setDynamicShortcuts` fails. Rust logs the false result but does not invalidate the cached fingerprint.
- **Consequence:** identical subsequent session metadata is suppressed indefinitely rather than retried after rate limiting ends. Renamed/deleted sessions can leave stale launcher shortcuts until another metadata change or cache reset. Sign-out is a separate path: `clear_index` sends an empty replacement and Java deliberately removes all dynamic shortcuts before its rate-limit check. Do not incorrectly describe rate limiting alone as bypassing that sign-out cleanup.
- **Bounded fix:** distinguish prepared versus successfully applied metadata, preserve failure for retry, and bound retry frequency rather than JNI-calling every frame. Cover failure -> unchanged metadata -> later success, deletion, and sign-out in tests. Exercise actual launcher replacement/rate limiting separately on the coordinator's emulator.
- **Evidence status:** concrete source defect, no runtime retry test found. Existing Spotlight fingerprint tests establish allocation/cache behavior, not successful Android publication.

### P1: Failed ongoing-agent notification is also cached as applied

- **Call chain:** `MobileApp::sync_live_activity` in `src/app/deep_link_glue.rs` -> `ios_ext::sync_live` in `src/ios_ext.rs` -> Android `imp::apply` -> JNI `syncLive` -> `AndroidServices.syncLive`.
- `sync_live` installs `LAST = state` before applying it. `syncLive` returns false when notifications are disabled, or when the JNI/UI operation fails. There is no failure propagation to `LAST`.
- **Consequence:** when permission is subsequently granted or a transient platform failure clears, the same agent state is never reapplied. This is a local-notification correctness gap independent of FCM. `nativeResume` refreshes settings and emits foreground, but neither invalidates this cache. A genuinely changed merged agent state can recover it, so the failure is not necessarily permanent.
- **Bounded fix:** acknowledge successful application before committing the content cache, with bounded retries and explicit permission/foreground invalidation. Test denied -> granted with identical content, failed empty-state cancellation, and account transition ownership. Do not implement a retry loop that repeatedly requests notification permission.
- **Evidence status:** concrete source defect, actual ongoing notification permission-recovery workflow untested.

### P1: Foreground appearance changes have no shared-settings invalidation

- **iOS reference:** `src/system.rs` installs foreground, Dynamic Type and Reduce Motion observers which set `NEEDS_REFRESH`.
- **Android current wiring:** `system::install` calls Android `imp::install`, which is empty. `nativeResume` in `src/android_services.rs` sets `NEEDS_REFRESH`; `system::poll` only rereads settings when that flag is set. `JcodeActivity` consumes `uiMode` in manifest `configChanges` but supplies no `onConfigurationChanged` callback to refresh shared settings. GPUI's `MainEvent::ConfigChanged` handler in `../gpui/crates/gpui_android/src/platform.rs` only resizes windows.
- **Consequence:** a night-mode configuration change delivered while the Activity remains resumed can redraw with stale `system::is_light` and stale orb theme until a later resume. A live animator-duration-scale change likewise has no settings observer. Font-scale recreation is a separate lifecycle case, not proven broken by this inspection.
- **Bounded fix:** wire configuration changes to shared-settings invalidation and request a frame. If live Reduce Motion support is intended, add a lifecycle-owned settings observer. Validate theme/orb updates without backgrounding, then verify observer teardown and resume behavior.
- **Evidence status:** concrete missing invalidation path, not an observed emulator failure. Existing rotation/background acceptance does not test changing appearance or animation settings while resumed.

## Missing entry surfaces, not just untested adapters

1. **Inbound Android share target is absent.** iOS `ios-ext/Sources/JcodeShare/ShareViewController.swift` collects text/URLs and forwards `jcode://new?text=...`. Android manifest declares MAIN and VIEW only. Neither `JcodeActivity` nor `AndroidServices.onResume` consumes ACTION_SEND/EXTRA_TEXT. Outbound `shareText` is the opposite direction and does not fill this gap. Adding an inbound share contract requires explicit UI/security behavior, bounded payload handling and signed-out behavior, not merely a broad intent filter.
2. **New-session/Ask shortcut donation is absent.** iOS `JcodeBridge/Bridge.swift` donates New/Ask activities. Android `ios_ext::imp::donate_shortcuts` is empty. Session dynamic shortcuts are not New/Ask actions. Raw `jcode://new` and `jcode://ask?text=...` parsing exists but does not make these entry surfaces discoverable.
3. **Per-agent Live Activity interaction has no Android equivalent.** `JcodeLive/LiveWidget.swift` links individual agent rows to sessions. Android receives only a headline string and opens MAIN. Any richer ongoing notification needs a deliberate privacy/ownership design rather than asserting feature equality from a visible notification.

## Suggested coordinator order

1. Repair success-aware shortcut and ongoing-notification caches with failure/recovery tests. Separately validate Java failure -> later success on an owned emulator.
2. Wire settings invalidation for consumed configuration changes; verify foreground theme/orb changes without a resume workaround.
3. Keep TalkBack and Rust/UI microphone workflows as real runtime gates. The isolated adapter successes are useful but insufficient.
4. Exercise local notification permission/delivery/tap/reply, real deep-link entry, native selection and browser authentication before claiming service completeness.
5. Decide product scope for inbound sharing, New/Ask shortcuts, richer ongoing interactions and background runtime. Record deliberate omissions explicitly.

## Implemented followthrough, November 15 at 08:14 UTC

The findings above record the original inspection, not the post-fix state. Shared fixes now acknowledge successful shortcut and ongoing-notification publication before deduplicating. Failed unchanged submissions retry after five seconds through a single scheduled GPUI wake, without frame-by-frame platform calls. Failed index clearing prevents private session republication, and live cancellation supersedes pending private content. Android foreground configuration changes, animator-duration changes, resume and notification-permission results enqueue settings invalidation onto the GPUI thread. Spotlight acknowledgement remains submission-only because its OS completion is asynchronous.

Inbound sharing now exposes only a `text/plain` ACTION_SEND filter. `AndroidServices.onResume` handles SEND before RemoteInput or data-URL fallback, including rejected payloads, and consumes/sanitizes the Intent once. The helper emits the proven draft-only shared contract `jcode://draft?text=...`, which preserves the incoming draft and other tabs without setting `auto_send`, including after connection. Ordinary `new`/`ask` routes retain existing send semantics. A `new?text=...&draft=1` URI is **not** this contract and still follows ordinary new-route behavior.

Validation: hosted `justrust test --lib` run `20261115-001215879-694113` passed **485 tests, zero failures, 11 ignored**. Hosted production `justrust check --lib` run `20261115-001240311-696066` passed. Focused system, live-cache/parser and deep-link tests passed separately, including failed publication recovery, urgent cancellation, one delayed wake, foreground GPUI invalidation and post-connect draft non-submission. Android production Java sources compiled with JDK 21 `javac --release 8` against SDK 36. These are source/unit/SDK checks, not emulator runtime proof. Integrated sharing additionally passed **152 pure host Java assertions**, including lossless query-injection-safe encoding, malformed/oversized payload rejection, consumed-intent replay rejection and distinct second-delivery acceptance. The harness checks the narrow manifest filter and SEND-before-fallback source contract. All Java sources compiled against SDK 36 after integration, and hosted shared deep-link tests passed 4/4 in run `20261115-001725531-715030`, including no submission after connection.

Coordinator runtime followthrough remains: deny then grant notifications with unchanged agent content, shortcut publication failure/recovery and deletion, foreground theme/animation changes without resume, and cold/warm Android share intent exactly-once draft ownership with no model request. No devices, notification delivery or FCM credentials were changed by this followthrough. The narrow share-filter configuration is enabled in source, not yet validated on a device.

This inspection makes no new Play/signing/production-release claim and does not alter the known FCM/backend transport gap.
